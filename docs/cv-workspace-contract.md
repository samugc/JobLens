# CV evidence workspace — parser contract 1.1 over HTTP transport 1.0

This document describes the response shape that `web/workspace/api-adapter.js`
accepts and normalizes. It is written against the **canonical parser contract
(schema 1.1)** and a thin **HTTP transport (transport 1.0)** that carries it over
HTTP.

- Parser schema version: `1.1`
- HTTP transport version: `1.0`
- Upload: `POST {base}/extractions` with `multipart/form-data`
- Optional read-back: `GET {base}/extractions/{job_id}`
- Default base: `/api/cv` (override with the
  `<meta name="joblens-cv-api-base" content="...">` tag in
  `web/workspace/index.html`)

The parser package defines no HTTP routes. The transport is the only part that
is not canonical; it adds the two identifiers and the version marker described
in [Transport 1.0](#transport-10).

Only the adapter knows the wire format; the rest of the workspace consumes the
normalized shape described in [Normalized shape](#normalized-shape).

The workspace never parses PDF or DOCX itself, never invents missing text and
never turns a failure into a success.

## Transport 1.0

The transport is a pass-through layer over the canonical parser response:

| Transport addition | Meaning |
| --- | --- |
| `transport_version` | Always `"1.0"`. Present so a future transport can change the HTTP shape without changing the parser schema. |
| `job_id` | Generated by the transport for the batch. The adapter uses it verbatim as the job id. |
| `document_id` | Generated by the transport for each document. The adapter uses it verbatim as the document id. |

The transport does not translate, re-order or re-label parser values. It returns
the canonical `batch` and `documents` objects unchanged and adds nothing else.

Identifiers are **transport-provided**. The adapter never substitutes a
client-generated identifier, so a document id from the transport can be traced
back to the batch that produced it.

## Upload

`POST {base}/extractions`

- Body: `multipart/form-data` with one or more `files` parts. The browser files
  are appended under the repeated field name `files`.
- At most **5** files per request. The workspace refuses more before sending.
- At most **25 MiB** in total. The workspace refuses a larger selection before
  building a request. See [Client-side batch limit](#client-side-batch-limit).
- Accepted extensions: `.pdf`, `.docx`.
- Headers sent by the adapter: `Accept: application/json` and
  `X-JobLens-Request: <token>`.
- Response: HTTP `2xx` with the terminal batch envelope below.

The POST response is terminal: it already contains every document, its status,
its warnings and its text. The workspace does **not** poll to obtain the result.

## Client-side batch limit

The parser's default limits are the canonical ones:

| Limit | Default |
| --- | --- |
| `max_documents` | 5 |
| `max_file_bytes` | 10 MiB |
| `max_batch_bytes` | 25 MiB |
| `max_text_chars` | 200000 |
| `max_pdf_pages` | 100 |
| `max_docx_paragraphs` | 20000 |
| `max_docx_xml_bytes` | 10 MiB |

The workspace mirrors **one** of them: the aggregate batch size.

- `CvApiAdapter.MAX_BATCH_BYTES` is `25 * 1024 * 1024`, the same value as the
  parser's default `max_batch_bytes`.
- `createExtraction` sums the size of the selected documents. A total of exactly
  the limit is allowed; a larger total is refused with `code: "batch_too_large"`
  **before** a request is built, so nothing is sent.
- The refusal uses the parser's own code, so the workspace and the parser
  describe the same condition the same way.
- The local transport accepts `max_batch_bytes + 1 MiB` for multipart framing,
  so a batch at the limit still reaches the parser and is parsed.

Everything else stays the parser's decision. The workspace does not apply
`max_file_bytes` per document, does not pre-empt `too_large`, and does not
decide any document status: those remain the parser's authority, reported back
as the document status and warnings they already were.

## Optional read-back

`GET {base}/extractions/{job_id}`

- `job_id` is URL-encoded by the adapter.
- Response: HTTP `2xx` with the same envelope.

This route is optional. It exists so a transport can answer a repeated request
for the same batch. `CvApiAdapter.waitForExtraction` is kept in the public
adapter surface for compatibility, but schema 1.1 has no non-terminal batch
status, so the workspace never needs it.

## Envelope

```json
{
  "schema_version": "1.1",
  "transport_version": "1.0",
  "job_id": "job-abc",
  "batch": {
    "status": "partial",
    "document_count": 2,
    "total_bytes": 27360,
    "status_counts": {
      "extracted": 1,
      "partial": 0,
      "empty": 0,
      "scanned_pdf": 0,
      "encrypted": 1,
      "malformed": 0,
      "unsupported_format": 0,
      "too_large": 0
    },
    "limits": {
      "max_documents": 5,
      "max_file_bytes": 10485760,
      "max_batch_bytes": 26214400,
      "max_text_chars": 200000,
      "max_pdf_pages": 100,
      "max_docx_paragraphs": 20000,
      "max_docx_xml_bytes": 10485760
    },
    "error": null
  },
  "documents": [
    {
      "document_id": "doc-abc-0",
      "index": 0,
      "filename": "sample-cv.pdf",
      "format": "pdf",
      "status": "extracted",
      "text": "Extracted text for this document.",
      "segments": [
        {
          "locator": { "kind": "page", "page": 1 },
          "text": "Extracted text for this document."
        }
      ],
      "warnings": [],
      "metadata": {
        "size_bytes": 18240,
        "page_count": 1,
        "paragraph_count": null
      }
    }
  ]
}
```

### Top-level fields

| Field | Required | Notes |
| --- | --- | --- |
| `schema_version` | yes | Must be exactly `"1.1"`. |
| `transport_version` | yes | Must be exactly `"1.0"`. |
| `job_id` | yes | Non-empty string, generated by the transport. |
| `batch` | yes | Batch outcome, counts and applied limits. |
| `documents` | yes | One object per uploaded document, in input order. |

### `batch`

| Field | Required | Notes |
| --- | --- | --- |
| `status` | yes | One of `completed`, `partial`, `rejected`. All three are terminal. |
| `document_count` | yes | Number of uploads supplied. Must equal `documents.length` for `completed` and `partial`; for `rejected` it keeps the submitted count, because nothing was processed. |
| `total_bytes` | yes | Non-negative integer. Sum of the supplied byte lengths. |
| `status_counts` | yes | Count per document status. Every status key is always present. For `completed` and `partial` the counts must sum to `documents.length`; for `rejected` every count is zero. |
| `limits` | yes | The limits applied to this request. |
| `error` | yes | `null` for `completed` and `partial`; `{"code", "message"}` for `rejected`. |

### `documents[]`

| Field | Required | Notes |
| --- | --- | --- |
| `document_id` | yes | Non-empty string, generated by the transport. |
| `index` | yes | Zero-based position in the input batch. |
| `filename` | yes | Sanitized basename only. |
| `format` | yes | `pdf`, `docx` or `unknown`. |
| `status` | yes | One of the eight parser document statuses. |
| `text` | yes | Extracted text, or `""` when unavailable. |
| `segments` | yes | Text blocks with source locators. |
| `warnings` | yes | Warning objects. May be empty. |
| `metadata` | yes | `size_bytes`, `page_count`, `paragraph_count`. |

`text` is always exactly `"\n\n".join(segment["text"] for segment in segments)`.
The adapter checks that invariant and raises a contract error when it does not
hold, rather than recomputing or repairing the text.

### `segments[]` and locators

Each segment has `{"locator": {...}, "text": "..."}`.

PDF locator, with 1-based page numbers:

```json
{ "kind": "page", "page": 2 }
```

DOCX locator, with 1-based paragraph numbers and the nearest preceding heading:

```json
{ "kind": "paragraph", "paragraph": 4, "section": "Experience" }
```

- `page` and `paragraph` are **1-based** integers.
- `section` is the nearest preceding Word heading, or `null` before the first
  heading. It is preserved verbatim and never invented.
- A segment without a valid locator is a contract error. The workspace does not
  guess a page or paragraph number.

### `metadata`

| Field | Type | Notes |
| --- | --- | --- |
| `size_bytes` | integer | Supplied document size. |
| `page_count` | integer or null | Total PDF pages; `null` for DOCX or unreadable input. |
| `paragraph_count` | integer or null | Total DOCX body paragraphs; `null` for PDF or unreadable input. |

## Status mapping

### Batch status

| Parser `batch.status` | Workspace job status | Notes |
| --- | --- | --- |
| `completed` | `complete` | Every document is `extracted`. |
| `partial` | `partial` | Processing finished, at least one document is incomplete. |
| `rejected` | *(error)* | Not a job. Raised as `CvBatchRejectedError` with the parser error code. |

### Document status

| Parser `document.status` | Workspace document status | Text |
| --- | --- | --- |
| `extracted` | `extracted` | non-empty |
| `partial` | `needs_review` | non-empty |
| `empty` | `failed` | `""` |
| `scanned_pdf` | `failed` | `""` |
| `encrypted` | `failed` | `""` |
| `malformed` | `failed` | `""` |
| `unsupported_format` | `failed` | `""` |
| `too_large` | `failed` | `""` |

`needs_review` means *text was returned but it is incomplete*. Every status that
produces no text is `failed`, so the reader never shows an empty document as
reviewable. The original parser status is preserved next to the visual status
(`parserStatus`) and is what the workspace displays as the reason.

Unknown statuses are rejected with a `CvContractError` instead of being mapped
to a friendly state, so contract drift is visible rather than hidden.

## Warnings

A warning is `{"code": "...", "message": "..."}`.

- `code` and `message` are required. Messages are fixed English text.
- The code list is open: a code the adapter does not know is **kept as is** and
  rendered from its message.
- Schema 1.1 defines no `severity` and no warning locator. The adapter does not
  invent either. If a future schema adds them, they are passed through
  unchanged.

Known codes are documented in the parser contract: `empty_document`,
`empty_pdf`, `scanned_pdf`, `pdf_encrypted`, `pages_without_text`,
`page_extraction_failed`, `page_limit_reached`, `paragraph_limit_reached`,
`no_body_paragraphs`, `text_truncated`, `document_too_large`,
`unsupported_format`, `non_word_ooxml`, `legacy_doc`, `malformed_document` and
`format_mismatch`.

## Errors and batch rejection

A rejected batch returns no documents and sets `batch.error`:

| Error code | Meaning | Suggested HTTP mapping |
| --- | --- | --- |
| `empty_batch` | No documents supplied. | 400 |
| `too_many_documents` | More than `max_documents` (default 5). | 400 |
| `batch_too_large` | Total bytes exceed `max_batch_bytes`. | 413 |

The adapter keeps the parser code. A rejection raises `CvBatchRejectedError`
with `code` set to the original parser code and `message` set to the original
`batch.error.message`, both when the transport returns it as a `2xx` body and
when it returns it as a non-`2xx` error body.

A rejected batch is validated on its own terms, separately from a completed or
partial batch:

- `documents` must be empty.
- `status_counts` must not count a processed document: every count is zero.
- `document_count` keeps the number of documents that were **submitted**. It is
  not compared with `documents.length`, because nothing was processed.
- `batch.error.code` and `batch.error.message` are preserved as they are.

The adapter never rewrites a count and never invents a placeholder document for
a rejected batch.

Other non-`2xx` responses raise `CvHttpError` with `status` and, when present,
the `code` from `error.code`. That includes the transport's own size refusal:
a body over the transport cap answers `413` with `error.code:
"request_too_large"`, which is reported as `CvHttpError` with `status: 413` and
`details.code: "request_too_large"`.

## Validation performed by the adapter

The adapter rejects the response with `CvContractError` when:

- `schema_version` is not `"1.1"` or `transport_version` is not `"1.0"`.
- `job_id` is missing or not a non-empty string.
- `batch.status` is not one of `completed`, `partial`, `rejected`.
- `batch.status_counts` is missing a status key or has a negative count.
- For a `completed` or `partial` batch: `batch.document_count` does not equal
  `documents.length`, or `batch.status_counts` does not sum to
  `documents.length`.
- For a `rejected` batch: `documents` is not empty, `batch.status_counts`
  counts a processed document, or `batch.error` is missing.
- `batch.error` is set on a non-rejected batch.
- A document is missing `document_id`, `index`, `filename`, `format`, `status`,
  `text`, `segments`, `warnings` or `metadata`.
- `document.format` is not `pdf`, `docx` or `unknown`.
- `document.status` is not one of the eight parser document statuses.
- A segment has no locator, or a locator without a 1-based `page` or
  `paragraph`.
- `document.text` does not equal the concatenated segment text.
- `metadata` is missing `size_bytes`, or `page_count` / `paragraph_count` is
  present but not a non-negative integer.

## HTTP responses

- `2xx`: the envelope above.
- Non-`2xx` carrying a rejected batch: `CvBatchRejectedError` keeping the
  parser code, message and submitted document count.
- Non-`2xx` with a known batch rejection code and no envelope: the same
  `CvBatchRejectedError`.
- Non-`2xx` otherwise, including `413 request_too_large`: `CvHttpError` with
  `status` and the reported code.
- Non-JSON body: `CvContractError`.
- Network failure: `CvError` with `code: "network_error"`.

## Normalized shape

The adapter returns the normalized job object. The UI only reads this shape:

```js
{
  id,                 // transport job_id
  status,             // complete | partial
  parserStatus,       // completed | partial
  schemaVersion,      // "1.1"
  transportVersion,   // "1.0"
  contractVersion,    // "1.1" (schema version, used by the contract badge)
  contractVersionMatches,
  documentCount,
  totalBytes,
  statusCounts,       // all eight parser statuses
  limits,             // the limits the parser applied
  batchError,         // { code, message } | null
  warnings: [],       // the parser reports no batch-level warnings
  error: null,
  documents: [{
    id,               // transport document_id
    index,            // parser index
    filename,
    format,           // parser format, the authority after extraction
    kind,             // pdf | docx | unknown, derived from format
    mediaType,
    status,           // extracted | needs_review | failed
    parserStatus,     // the original parser status
    sizeBytes, pageCount, paragraphCount,
    metadata,         // the parser metadata object
    warnings: [{ code, message, severity: null, locator: null }],
    error: null,
    fullText,         // the exact parser text
    segments: [{ id, text, locator, wordCount }]
  }]
}
```

The normalized job does **not** keep a deep copy of the raw response. The
parser text is available once, in `document.fullText` and in the segments, so
the CV content is not duplicated inside the job object.

Locators are normalized to `{ kind: "page", page, paragraph: null, section: null }`
or `{ kind: "paragraph", paragraph, page: null, section }`.

## Format authority

`document.format` is the authority after extraction. The filename extension is
only a hint for the *pre-upload* check. A DOCX file named `cv.pdf` is parsed as
DOCX, the parser reports `format: "docx"` with a `format_mismatch` warning, and
the workspace labels it as a DOCX.

## Changing the contract

1. Diff the new field names, statuses and locator shape against this document.
2. Update only `web/workspace/api-adapter.js`:
   - `SCHEMA_VERSION`, `TRANSPORT_VERSION`, `CONTRACT_VERSION`,
   - `BATCH_STATUSES`, `PARSER_DOCUMENT_STATUSES`, `DOCUMENT_FORMATS`,
   - `PARSER_DOCUMENT_STATUS_TO_VISUAL`, `BATCH_STATUS_TO_VISUAL`,
   - the `normalize*` functions and the validation rules,
   - the upload field name and route in `createExtraction`.
3. Update `web/workspace/fixtures/*.json`.
4. Update `tests/ui/cv-workspace.test.mjs` and `tests/test_cv_workspace_assets.py`.
5. Update this document and leave a short note in `docs/cv-workspace.md`.

No other workspace file should need to change. If it does, the adapter is
leaking wire-format details and that should be fixed first.
